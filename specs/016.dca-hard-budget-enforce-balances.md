# 016 — DCA backtest with a hard budget (`enforceBalances`)

Feature spec. Origin: a community request with a patch against 1.31.1 (reviewed
and taken as the starting point).

## §1 Problem

The DCA engine opens every deal and fills every DCA order whatever the balance,
and only warns "The bot used more funds than allocated". The live bot checks the
balance and skips orders it cannot pay for, so backtest and live results split as
soon as the money runs out (long drawdowns).

## §2 Behaviour (`DCABacktestingInput.enforceBalances === true`)

- §2.1 The budget is the passed `balances[].free` of the asset the bot spends:
  quote for a long, base for a short. No row for that asset ⇒ no budget applies.
- §2.2 Free budget = budget + profit realised in that asset − what every open deal
  spending that asset holds. Shared across pairs of a multi-pair bot.
- §2.3 A deal opens only if the free budget pays for its base order (a long pays
  `qty × price × (1 + fee)`, a short sells `qty`). Otherwise it is skipped, counted,
  and the cooldown clocks set for it are restored.
- §2.4 On each DCA pass, in fill order, each DCA order must fit in what the orders
  before it left. A refused order is dropped from the deal's active orders, so it
  cannot fill later at a different price. A re-generated order for the same level
  (indicator-driven DCA) is tried again and counted as another attempt.
- §2.5 Closing a deal returns its proceeds, profit included (follows from §2.2).
- §2.6 Profit % and drawdown bases use the budget (`initialBalanceUsd` = budget).
- §2.7 Futures and combo bots ignore the flag; the run is byte-identical to a run
  without it.

## §3 Off by default

- §3.1 Absent or `false`: the engine runs exactly as before (fingerprint-equal).
- §3.2 A budget that is never reached changes no deal.

## §4 Result

- §4.1 `budgetLimit: { asset, budget, dealsSkipped, dcaRefused, dcaRefusedAttempts }`
  is present only when a budget applied (§2.1). `dcaRefused` counts distinct
  deal + level pairs; `dcaRefusedAttempts` counts every refusal.
- §4.2 When anything was refused, a `messages` line states the same counts, so a
  saved result whose store drops `budgetLimit` still carries them.

## §5 Parity (Danger List #13)

Server-side (main-app) and browser (dashboards) runs use the same engine. A host
that does not pass the flag gets §3.1 behaviour, so a consumer pinned to this
version without wiring the flag is unchanged.

## Open decisions (resolved in the plan)

- Retry semantics of a refused level (§2.4).
- Whether main-app's server-side / API / MCP backtest exposes the flag.
- Wallet-at-end figure.

## Invariants

None: the engine is a pure library and persists nothing. The dashboard strips
`budgetLimit` before saving a result (the backend input type has no such field);
the counts persist only inside the existing `messages` strings.
