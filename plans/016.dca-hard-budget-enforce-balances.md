# 016 — plan: DCA hard budget

## Build order

1. backtester: flag on `DCABacktestingInput`, threaded to `StrategyInput`; per-run
   counters on `StrategyContext`; checks in `openDeal` and `processDCAOrders`;
   budget as balance/profit base; `budgetLimit` on the result. (Community patch +
   the structured result field and level-keyed distinct count.)
2. Ship backtester by push; the pipeline's library bump moves the consumers' lock pins.
3. main-dash-redesign core: optional **Budget** field on the full backtest dialog
   (local mode, spot DCA, one spend asset); passes `enforceBalances` + a balances
   list with the spend asset's `free` replaced by the budget; result Overview shows
   the counts; `budgetLimit` stripped before the remote save.

## Decisions on the spec's open questions

- §2.4 retry: keep the patch's semantics (dropped for that pass; a regenerated
  order is tried again and counted as an attempt). Distinct count is the headline.
- main-app server-side/API/MCP: not wired in v1. The dashboard disables the field in
  Server mode. Flag-off parity (§5) keeps both paths identical for every run that
  can reach the server.
- Wallet at end: not added (the brief asks for refused counts only).

## Blast Radius

1. Call sites: `openDeal`, `processDCAOrders`, the balance/profit base in deal
   start, `maxTheoreticalUsageWithRate`, result build — all gated on `budgetRow()`,
   which is null unless the flag is on, spot, non-combo, with a matching balance row.
2. No `core/` submodule in this repo.
3. Contract: `DCABacktestingInput` / `DCABacktestingResult` (Danger #13) — both
   additions are optional fields. main-app's server-side wrapper passes neither.
4. Whole suite must stay green; `file-mode-golden`, `hooks-parity` and the
   fingerprint tests pin flag-off behaviour.
